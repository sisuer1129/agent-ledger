# 新增账户功能恢复设计

## 背景与结论

当前后端仍提供 `POST /accounts` 新增账户接口，但前端账户列表没有“添加账户”入口，账户弹窗的保存逻辑也被固定为 `PUT /accounts/{id}`。早期设计文档包含新增账户入口与弹窗，而 Git 历史没有显示一次明确的主动删除。因此，本次按前端迁移遗漏/回归处理，不涉及数据库迁移。

## 方案比较

1. **复用现有账户弹窗（采用）**：桌面端和移动端增加入口；无账户 ID 时为新增模式，有 ID 时保持编辑模式。改动最小，与现有 UI 和 API 一致。
2. **新建独立页面或分步向导**：适合更复杂的账户开通流程，但对当前字段量过度设计，也会增加移动端导航成本。
3. **只在设置页增加入口**：实现最简单，但账户管理入口隐蔽，与用户在首页查找账户操作的习惯不符。

## 交互与界面

- 桌面端：在“账户”列表标题右侧增加“添加账户”按钮。
- 移动端：在首页账户列表顶部增加同等入口，无账户时仍可直接新增。
- 新增模式：标题显示“添加账户”，显示“初始余额”，隐藏“停用账户”。默认账户类型为储蓄卡，预算周期为自然月，还款月份为下月，初始余额为 0。
- 编辑模式：标题显示“账户设置”，保持现有字段和停用操作；不允许通过编辑重置初始余额。

## 数据流与错误处理

- 新增：账户 ID 为空时，整理表单数值后调用 `POST /accounts`。初始余额空值按 0 处理。
- 编辑：账户 ID 存在时，仍调用 `PUT /accounts/{id}`，不发送初始余额。
- 新增成功后刷新账户、概览、预算与移动端首页，并选中新账户。
- API 验证错误继续交由现有状态提示显示；失败时弹窗不关闭，避免用户重复输入。

## 验证范围

- 合同测试覆盖：桌面/移动新增入口、新增模式字段、POST/PUT 分流、新增数值规范化。
- 原有账户编辑、停用和交易功能不得回归。
- 运行全部 Python 与前端测试、静态/语法检查，再做一次桌面和移动端的真实浏览器操作验证。

## 发布边界

源码验证通过后先更新 GitHub `main`，再以该提交制作可回滚的 NAS 更新包。本次不直接修改线上数据，也不在未验证 NAS 部署结果时声称生产环境已更新。
